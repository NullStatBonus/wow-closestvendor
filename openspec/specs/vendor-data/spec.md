# vendor-data Specification

## Purpose
Provide a compact, offline-generated dataset of vendors that can buy items or repair gear, with coordinates usable for distance comparison and waypointing, from sources whose licenses permit redistribution in an MIT project.

## Requirements

### Requirement: Eligible vendors only
The dataset SHALL contain only NPCs listed as vendors or repairers in the source, and SHALL exclude all other NPCs.

#### Scenario: Non-vendor NPC in source
- **WHEN** the build processes an NPC that is in neither the vendor nor the repair list
- **THEN** it is not present in the output

#### Scenario: Repair-capable vendor
- **WHEN** the build processes an NPC in the repair list
- **THEN** it is present and marked repair-capable

#### Scenario: NPC without coordinates
- **WHEN** a listed vendor has no coordinates in the source
- **THEN** it is omitted from the output

### Requirement: Vendor record fields
Each record SHALL include NPC id, name, UI map id, normalized (0-1) map coordinates, faction availability, a repair flag, and an ammo seller flag.

#### Scenario: Record usable for waypoint
- **WHEN** a vendor is chosen as target
- **THEN** its stored UI map id and normalized coordinates are sufficient to create a waypoint without further conversion

### Requirement: Ammo seller flags
Each record SHALL say whether the vendor sells arrows, bullets, both or neither, taken from the source's sold-by lists for the standard vendor ammo.

#### Scenario: Arrow vendor
- **WHEN** the source lists a vendor as selling a standard arrow
- **THEN** its record marks arrows

#### Scenario: Non-seller
- **WHEN** a vendor sells no standard arrow or bullet
- **THEN** its record marks no ammo

### Requirement: Reproducible build
The dataset SHALL be generated by a committed script from a documented source and wago map data, and SHALL record the source and its version in the output header.

#### Scenario: Rebuild
- **WHEN** the build script is re-run with the same inputs
- **THEN** it produces an identical output file

### Requirement: License compliance
The repository SHALL be MIT licensed, SHALL keep the source's license and copyright notice in `THIRD_PARTY.md`, and SHALL NOT include data from sources whose licenses are incompatible with MIT.

#### Scenario: Attribution present
- **WHEN** the generated data is shipped
- **THEN** `THIRD_PARTY.md` contains the source's copyright notice and license text

### Requirement: Swappable data source
The addon SHALL read vendor data only through the generated data file's record contract, and the build SHALL separate reading a source from writing the file, so replacing the source requires no change to addon code.

#### Scenario: New source
- **WHEN** a different source produces records in the same normalized shape
- **THEN** the same writer emits a valid data file that passes the data checks

#### Scenario: Invalid record
- **WHEN** a record has coordinates outside 0-1, an unknown faction, or a duplicate NPC id
- **THEN** the build fails instead of writing the file

### Requirement: Shared dataset across flavors
The addon SHALL ship one dataset used by both Classic Era and WoW Forever, and SHALL ignore records whose UI map does not exist on the running client.

#### Scenario: Map missing on client
- **WHEN** a record references a UI map the client does not know
- **THEN** the record is skipped without error

### Requirement: Reagent seller flags
Each record SHALL say which of the watched class reagents the vendor sells, taken from the source's sold-by lists for those items.

#### Scenario: Reagent vendor
- **WHEN** the source lists a vendor as selling Arcane Powder
- **THEN** its record marks that reagent

#### Scenario: Non-seller
- **WHEN** a vendor sells none of the watched reagents
- **THEN** its record marks no reagent

#### Scenario: Reagent without any seller
- **WHEN** the source lists no vendor for a watched reagent
- **THEN** the build reports it so the reagent can be reviewed
